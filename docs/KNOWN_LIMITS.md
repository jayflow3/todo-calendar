# 알려진 한계

이 앱은 **서로 신뢰하는 내부 구성원만 접근하는 환경**에서만 쓰는 것을 전제로 합니다. 아래 한계는 앱 기능만으로 해결되지 않으며, 알고 수용한 사항입니다(PRD 6.2, 7.4).

## 1. 작성자 식별의 한계 (로그인 없음)

- 이름은 본인 확인 수단이 아닙니다. **누구나 다른 사람 이름을 골라 그 사람 명의로 작성·수정할 수 있습니다(사칭 방지 불가).**
- 같은 이름의 다른 사람을 구분하는 것은 라벨 입력에 의존하며, 잘못 선택해도 시스템이 막을 수 없습니다.
- 누가 어떤 기기에서 작업했는지 신뢰할 수 있는 감사 기록이 없습니다. `created_by`, `updated_by`, `author_id`, `task_events.actor_id`는 「누가 입력했다고 선택했는지」일 뿐입니다.
- 브라우저 저장소를 지우거나 기기를 바꾸면 이름 선택을 다시 해야 합니다.
- 추후 사칭 방지가 필요해지면 인증(SSO 또는 이메일 로그인) 도입이 필요하며, 이는 현재 범위 밖입니다.

## 2. RLS(행 수준 보안)의 한계

- 로그인이 없으면 RLS가 사용자를 구분할 수 없습니다. 즉 **anon key와 URL을 아는 사람은 허용된 범위 안에서 모든 데이터를 읽고 쓸 수 있습니다.**
- RLS는 「허용하는 동작의 종류」와 「데이터 형식」을 제한할 뿐 신원을 보장하지 않습니다. 이 앱의 정책은 다음으로 제한됩니다.

  | 테이블 | 허용 | 허용하지 않음 |
  | --- | --- | --- |
  | `tasks` | 조회·등록·수정 | 삭제(소프트 삭제는 `deleted_at` 수정으로 처리) |
  | `comments` | 조회·등록 | 수정·삭제 |
  | `members` | 조회·등록 | 수정·삭제 |
  | `task_events` | 조회·등록 | 수정·삭제 |

- anon key는 브라우저 번들에 들어가므로 누구나 열어 볼 수 있다고 가정합니다. service role key 같은 관리자 키는 어떤 경우에도 클라이언트·저장소에 두지 않습니다.

## 3. 그래서 필요한 접근 범위 제한

앱을 사내망/VPN 또는 IP 허용 목록 뒤에 두는 것이 필수에 가깝습니다(자세한 방법은 [OPERATIONS.md](OPERATIONS.md)).

- 검색 엔진 노출 차단(`noindex`)은 적용되어 있지만 접근 통제는 아닙니다.
- URL을 부서 밖에 공유하지 않습니다.
- 부서원이 바뀌면 키 교체 절차를 따릅니다.
- 병가·경조사 등 개인 사유는 제목·설명·댓글에 적지 않습니다(저장 대상은 이름과 업무 내용뿐).

## 4. 구현상의 한계

- **부서원 비활성은 앱에서 할 수 없습니다.** PRD 7.4가 `members`에 조회·등록만 허용하므로, 비활성(`active=false`) 처리는 운영자가 SQL로 합니다(PRD 확인 필요 항목).
- 소프트 삭제 시각(`deleted_at`)은 클라이언트 시계로 기록됩니다. 생성·수정·완료 시각은 서버가 기록합니다.
- 동시 편집은 필드 단위 last-write-wins입니다. 같은 필드를 동시에 고치면 나중에 저장한 값이 남고, 이전 값은 `task_events`(상태·담당자·마감일·우선순위)에서만 확인할 수 있습니다. 제목·설명·카테고리의 이전 값은 남지 않습니다.
- 연결이 끊긴 동안(오프라인) 편집은 지원하지 않습니다. 끊기면 배너가 뜨고 30초마다 재조회만 합니다.
- 무료 플랜 Supabase 프로젝트는 활동이 없으면 일시정지될 수 있습니다(PRD Q2).
