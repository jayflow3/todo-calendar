# 테스트 보고서 (단계 5 점검 + 실제 DB 검증)

실행 환경: Windows 11, Node 24, **Microsoft Edge(Chromium) 최신판**, 로컬 정적 서버(gzip, HTTP/1.1). 화면·접근성·반응형·성능은 local 어댑터로, DB 계약과 supabase 어댑터는 **로컬 PostgreSQL 17.5 + PostgREST 16.4**(아래 「실제 DB 검증」)로 확인했습니다. 모든 수치는 이 환경에서 실제로 측정한 값입니다. 실행하지 못한 항목은 「미검증」으로 표시했습니다.

## 7.2 성능 (1,000건, 가정: 동시 사용자 ≤ 20명)

초기 로드는 캐시를 끄고 Fast 4G(9Mbps/165ms)와 Slow 4G(1.6Mbps/150ms)를 에뮬레이션해 측정했습니다. 필터 갱신은 「입력 → 렌더 → 첫 페인트」까지, 즉 사용자가 결과를 처음 보는 시점으로 쟀습니다(처음에는 JS 실행 시간만 재서 실제보다 좋게 나왔고, 이를 고쳤습니다).

| 항목 | 목표 | 측정(실행 3~5회 범위) | 판정 |
| --- | --- | --- | --- |
| LCP | 2.5초 이하 | 0.49~0.60초 | 통과 |
| 첫 데이터 표시 | 3초 이내 | **1.00~1.04초** (요청 7개, HTTP/1.1). 번들 전에는 2.07~2.26초(요청 43개) | 통과 |
| 첫 화면 JS·CSS 전송(gzip) | 300KB 이하 | **35.0KB** (supabase 어댑터 사용 시 vendor +28.4KB = 63.5KB) | 통과 |
| 필터·검색 → 첫 페인트, **p50** | 100ms 이내 | 리스트 54~69, 칸반 61~79, 캘린더 52~57, 대시보드 25~32 ms | 통과 |
| 필터·검색 → 첫 페인트, **p95**(20회) | 100ms 이내 | 리스트 73~116, 칸반 78~107, 캘린더 72~83, 대시보드 48~65 ms (최대 133ms) | **불안정**(리스트·칸반이 100ms 근처~초과) |
| INP 근사(상호작용 13회, 새 페이지 3회 중앙값) | 200ms 이하 | 중앙값 88~168ms, **최악 176~456ms**(첫 대화상자 열기 등 콜드 스타트) | 중앙값 통과 / **최악값 초과** |
| 실시간 반영 | 3초 이내 | 122~365ms | 통과 |
| 저장 응답 p95 | 500ms 이하 | local 어댑터 0.5~1.6ms. 실제 DB 구간은 별도 측정하지 않음 | **Supabase 서버 기준은 미검증** |

해석과 한계:

- 같은 코드라도 이 PC의 부하에 따라 수치가 크게 달라집니다(병렬 실행 시 3배까지). 그래서 성능 측정은 일반 e2e와 분리했습니다(`npm run test:perf`, 다른 작업 없이 실행).
- 개선한 것: 칸반을 열마다 100장으로 제한, 칸반 카드에 `content-visibility`, **하나의 번들(`dist/app.js`)로 묶기**(요청 43개→7개, 첫 데이터 표시 약 2.2초→약 1.0초), **점진 렌더링**(결과의 앞 40행·열마다 15장을 먼저 그리고 나머지는 다음 프레임들에 붙임: 리스트 p50 약 125ms → 약 55ms, 칸반 약 85ms → 약 60ms). 도메인 계산(필터·정렬·통계)은 1,000건에서 1ms 미만이라 병목이 아니고, 병목은 DOM 생성·레이아웃입니다.
- **번들이 필터 갱신을 느리게 만들지는 않았습니다.** 번들 적용 직후 수치가 나빠 보여(리스트 p50 100~150ms), 같은 시점에 이전 ES 모듈 버전을 별도 작업 폴더에서 같은 테스트로 3회 비교했습니다. 이전 버전도 똑같이 느렸습니다(리스트 p50 96~132ms vs 번들 105~151ms). 그 시간대에 이 PC가 전반적으로 느려진 것(측정 환경 잡음)이며, 그래서 절대 수치보다 같은 시점의 상대 비교를 믿어야 합니다. 이 PC가 한가할 때 측정한 앞선 수치(p50 약 55~69ms)가 코드의 실제 성능에 가깝습니다.
- 최악값은 대부분 **처음 한 번의 콜드 스타트 상호작용**(첫 대화상자 열기·첫 칸반 렌더)입니다. 같은 동작을 두 번째부터는 50ms 안팎이었습니다.
- 검색 입력 지연 측정에 한글을 쓰면 앱의 long task 없이 300ms 대기가 보였고(`input→처리 0`), 이를 Playwright의 한글 합성 입력 쪽 현상으로 판단해 INP 측정 입력만 숫자로 바꿨습니다. **이 판단은 확정하지 못했습니다.** 실제 한글 입력에서 지연이 있는지는 실기기에서 확인해야 합니다.
- 저사양 모바일 CPU(스로틀링)에서의 측정은 하지 않았습니다 → **미검증**.

## 실제 DB 검증 (로컬 PostgreSQL 17.5 + PostgREST 16.4)

Docker·클라우드 계정 없이 확인하려고 npm `embedded-postgres`와 PostgREST 공식 바이너리를 별도 폴더에 받아, Supabase 프로젝트가 만들어 두는 역할(`anon`, `authenticator` 등)·기본 권한·`supabase_realtime` publication을 흉내 낸 뒤 `0001_init.sql`을 적용했습니다. 브라우저의 supabase 어댑터는 `/rest/v1` 경로를 이어 주는 작은 프록시를 거쳐 이 DB에 연결했습니다.

| 확인한 것 | 결과 |
| --- | --- |
| `0001_init.sql` 실제 실행(테이블·제약·트리거·RLS·권한·publication) | 오류 없이 적용 |
| 제약: 이름 21자·빈 이름·라벨 11자, 제목 빈 값/공백/101자, 설명 2001자, 잘못된 상태·우선순위, 없는 부서원(FK), 댓글 빈 값/1001자 | 모두 거부(경계값 100자·2000자는 허용) |
| 트리거: 공백 정리, `updated_at` 서버 갱신(클라이언트가 보낸 1999년 값 무시), `completed_at` 기록·해제·보존, `created_by` 변경 불가, 변경 이력(`task_events`) 자동 기록 | 통과 |
| RLS: 모든 테이블 DELETE 거부(행이 실제로 남음), 댓글·부서원·이력 수정 거부, 허용 목록 밖 테이블 접근 불가 | 통과 |
| **음성 대조**: `tasks`에 DELETE 권한·정책을 일부러 열고 같은 테스트 실행 | 테스트가 **실패**했고, 원복하면 다시 통과 |
| 실제 supabase 어댑터(브라우저): 등록·수정·상태 변경·댓글·변경 이력·소프트 삭제와 되돌리기, 새로고침 후 유지 | 통과 |
| 동시 편집 3종(다른 필드 병합, 같은 필드 확인창, 삭제 우선) — `updated_at` timestamptz 문자열 비교 포함 | 통과 |
| 다른 사용자 변경의 포커스 재조회 반영과 「○○님이 수정함」 | 통과 |
| 운영 문서의 SQL: 확인 쿼리 3종, `kpi.sql` 쿼리 5개(K1·K2 8주 추이·K3·K4), 부서원 비활성, 90일 정리(할일·댓글·이력 1건씩 → 0건) | 모두 의도대로 동작 |
| `supabase/seed.sql`: 빈 DB에서 실행 → 부서원 6·할일 20·댓글 4, 완료 4건의 `completed_at` 트리거 기록, 재실행 시 건너뜀 | 통과 |
| `supabase_realtime` publication에 `tasks`, `comments` 포함 | 확인 |

**이 검증으로 찾아 고친 버그:** 다른 사람이 이름을 새로 등록한 뒤 변경하면, 이미 열려 있던 화면은 부서원 목록을 갱신하지 않아 알림이 「다른 사람님이 …」로 나오고 **그 사람이 담당자인 할일이 「미배정」으로 보였습니다.** local 어댑터 테스트는 부서원이 처음부터 시드되어 있어 드러나지 않았습니다. 동기화할 때 부서원도 함께 불러오도록 고쳤고, local 모드 회귀 테스트도 추가했습니다(수정을 빼면 실패하는 것까지 확인).

이 환경과 실제 Supabase의 차이: Supabase Auth·API 게이트웨이·**Realtime(WebSocket)** 서버는 없습니다. 역할·권한은 Supabase 문서 기준으로 흉내 낸 것이며 PostgREST 버전도 다를 수 있습니다. 같은 테스트(`npm run test:db`)를 실제 프로젝트에 `SUPABASE_URL`/`SUPABASE_REST_URL`과 anon 키로 그대로 실행할 수 있습니다.

## 기능 시나리오 (단계별 e2e)

작성자 식별·등록·수정·삭제·되돌리기·댓글, XSS(제목·설명·댓글·이름), 입력 검증, 세 뷰 항목 일치, URL 복원, 드래그·키보드 상태 변경과 실패 시 되돌림, 긴급 배지 경계, 캘린더(+N개·날짜 클릭·마감일 없음·월 이동), 대시보드 카드↔리스트 건수 일치, 두 사용자의 동시 편집 3종((a) 다른 필드 병합, (b) 같은 필드 확인창, (c) 삭제 우선), 연결 끊김 배너와 폴링 복구, 새 부서원 이름 표시 회귀.
